# Gala Dinner — Registration & Live Admin Dashboard

A production-ready guest registration system for a gala dinner in Amman.

- **Public form (`/`)** — mobile-first. Guests submit a photo, first/last name, email and phone from their phones.
- **Admin dashboard (`/admin`)** — auth-protected. Shows every submission and updates **in realtime** via Supabase Realtime (new registrations appear within ~2s, no refresh), with check-in toggling, search and CSV export.

## Stack

- Next.js 15 (App Router, TypeScript strict)
- Tailwind CSS v4
- `@supabase/supabase-js` v2 + `@supabase/ssr` for auth session handling
- Deploy target: Vercel **or** Cloudflare Workers (via the OpenNext adapter)

No extra UI libraries, ORM or state library.

## Security model

- The **anon** key (shipped to the browser) can only **INSERT** registrations and **upload** photos — nothing else.
- Guest PII (names, emails, phones) is readable only by the **authenticated admin** (RLS `admin_select` / `admin_update`). The anon key returns an empty result for `select` — verified with curl below.
- Photos live in a **public** storage bucket for simplicity. The guest-facing photo URLs are public.
  - **Hardening step (if needed):** switch the `photos` bucket to private and serve images through short-lived **signed URLs** generated by the authenticated admin. Drop the `public_read_photos` policy and have the dashboard call `createSignedUrl` instead.
- The **service role key is never used in the app** and never placed in client code or `NEXT_PUBLIC_*` env vars.

Verify the RLS boundary against your project:

```bash
URL="https://<your-ref>.supabase.co"
ANON="<your-anon-key>"

# Expect: []  (anon cannot read registrations)
curl -s "$URL/rest/v1/registrations?select=*" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"

# Expect: HTTP 201 (anon may insert)
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$URL/rest/v1/registrations" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON" \
  -H "Content-Type: application/json" -H "Prefer: return=minimal" \
  -d '{"first_name":"A","last_name":"B","email":"a@b.dev","phone":"+962790000000","photo_url":null}'
```

## Environment variables

**No setup required to run or deploy.** The project's Supabase URL and public
anon key are committed as built-in defaults in
[`lib/supabase/config.ts`](lib/supabase/config.ts), so the app builds and
deploys with zero environment configuration. These are public, client-safe
values (the anon key ships in the browser bundle either way; RLS is what
protects the data).

To point the app at a **different** Supabase project, set either env var — they
always take precedence over the built-in defaults:

```
NEXT_PUBLIC_SUPABASE_URL=https://<your-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<your-anon-key>
```

Locally, put them in `.env.local` (see `.env.example`). On Vercel / Cloudflare,
add them as **build** variables. Find the values in the Supabase dashboard under
**Project Settings → API**. The secret **service role** key is never used by
the app and must never be added here.

## Database / migration

The schema lives in [`supabase/migrations/0001_init.sql`](supabase/migrations/0001_init.sql)
and is **already applied** to the live `gala-dinner` project. To provision a new
project, run that file in the Supabase **SQL editor**, or with the CLI:

```bash
supabase db push   # or paste the file into the SQL editor
```

It creates the `registrations` table, RLS policies, the public `photos` storage
bucket and its policies, and adds the table to the `supabase_realtime`
publication (required — without it the dashboard receives no events).

## Creating the admin user

The dashboard signs in with Supabase email/password auth. Create the admin in
**Dashboard → Authentication → Add user** (set "Auto Confirm User"), or via the
Admin API with your service role key (keep it server-side only):

```bash
curl -X POST "$URL/auth/v1/admin/users" \
  -H "apikey: $SERVICE_ROLE_KEY" \
  -H "Authorization: Bearer $SERVICE_ROLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"<strong-password>","email_confirm":true}'
```

Then sign in at `/admin/login`.

## Run locally

```bash
npm install
npm run dev
# http://localhost:3000        → public form
# http://localhost:3000/admin  → dashboard (redirects to /admin/login if signed out)
```

Production build:

```bash
npm run build && npm start
```

## Deploy to Vercel

1. Push this repo to GitHub.
2. In Vercel, **New Project → Import** the repo. Next.js is detected automatically.
3. Add the two environment variables (`NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY`) under **Settings → Environment Variables**.
4. Deploy. No extra build configuration is required.

## Deploy to Cloudflare Workers

This app runs full SSR + middleware, so it deploys to **Cloudflare Workers**
(not static Pages) via the [OpenNext](https://opennext.js.org/cloudflare)
adapter (`@opennextjs/cloudflare`). Config lives in `wrangler.jsonc` and
`open-next.config.ts`; both are already wired up.

**Option A — Connect the Git repo (recommended for continuous deploys)**

1. Push this repo to GitHub.
2. Cloudflare dashboard → **Workers & Pages → Create → Import a repository** →
   select this repo. It detects Next.js and the OpenNext adapter.
3. Confirm the build/deploy command is `npx opennextjs-cloudflare build` /
   `npx wrangler deploy` (or `npm run deploy`).
4. Deploy. No environment variables are required — the Supabase config is
   committed as a built-in default. (Only set `NEXT_PUBLIC_*` **build**
   variables here if you want to point at a *different* Supabase project;
   `NEXT_PUBLIC_*` values are inlined at build time.)
5. You get a `*.workers.dev` URL; add a custom domain if you like.

**Option B — Deploy from your machine**

```bash
npm install
npx wrangler login          # one-time auth
npm run deploy              # builds with OpenNext and deploys
```

`npm run deploy` works as-is — the Supabase config has a committed default.
(Set `NEXT_PUBLIC_*` in `.env.local` only to target a different project.)

**Preview the Workers runtime locally**

```bash
npm run preview            # builds + runs in workerd via wrangler dev
```

> The compatibility date in `wrangler.jsonc` is set with the `nodejs_compat`
> flag, which the Supabase client requires on Workers.

## How realtime stays authenticated

With RLS enabled, an **unauthenticated** realtime socket silently receives no
rows — the most common "the dashboard never updates" bug. The dashboard fetches
the current session and calls `supabase.realtime.setAuth(access_token)` before
subscribing, and middleware refreshes the session cookie on every request, so
the `postgres_changes` stream is always authorized. RLS is never weakened to
"make realtime work".

## Internationalization

All user-facing strings are centralized in [`lib/strings.ts`](lib/strings.ts) so
the app can be re-skinned or translated (Arabic / RTL) from one place later.
